**دعوة واضحة. حضور منظّم.**

## التشغيل المحلي

المتطلبات: **Node.js 20+** و**Java 11+** (لمحاكي Firestore الرسمي؛ ماك: `brew install openjdk@21`).

```bash
npm install
npm run dev:local
```

بلا أي حساب Firebase: يشغّل محاكي Firestore الرسمي مع **حفظ البيانات بين التشغيلات** (`.emulator-data/`)، ويعبّئ البيانات التجريبية أول مرة ويطبع روابط التجربة، ثم يفتح المنصة على `http://localhost:3000` مع عامل المهام كل 15 ثانية.

- من جوال على نفس الشبكة: `npm run dev:local -- --lan` (الكاميرا تحتاج HTTPS؛ البدائل اليدوية تعمل، أو استخدم Codespaces).
- **GitHub Codespaces (من الجوال):** Code ← Codespaces ← Create. إعداد `.devcontainer/` يثبّت Java ويشغّل كل شيء، ويضبط `APP_URL` على رابط HTTPS للمنفذ 3000 (فتعمل الكاميرا وإجراءات الخادم خلف الوسيط). لمشاركة الدعوات مع أجهزة أخرى اجعل المنفذ **Public** من تبويب Ports.

| الأمر | الوظيفة |
|---|---|
| `npm test` | الاختبارات الآلية على محاكي Firestore (منفذ 8085، لا تمس قاعدة حقيقية) |
| `npm run test:e2e` | الرحلة كاملة في متصفح حقيقي على بناء إنتاجي (يحتاج ffmpeg) |
| `npm run seed` | البيانات التجريبية (لا تتكرر) |
| `npm run worker` | عامل المهام مستقلًا |
| `npm run typecheck` · `npm run lint` | الفحص |

## الإعداد على Firebase + Vercel

**1) مشروع Firebase وقاعدة Firestore**
1. [console.firebase.google.com](https://console.firebase.google.com) ← **Add project**.
2. **Build ← Firestore Database ← Create database**.
3. **Production mode** (يمنع أي وصول من المتصفحات — وهذا المطلوب).
4. الموقع **`europe-west3` (Frankfurt)** — لا يتغير بعد الإنشاء (راجع القرار المفتوح عن PDPL).
5. (اختياري) انشر القواعد من المستودع: `npx firebase deploy --only firestore:rules --project <PROJECT_ID>` — الملف [`firestore.rules`](firestore.rules) فيه `allow read, write: if false`.

**2) مفتاح حساب الخدمة**
1. **Project settings ⚙ ← Service accounts ← Generate new private key** (يُنزَّل JSON).
2. ⚠ **سرّي**: لا تضعه في المستودع (أنماطه في `.gitignore`).
3. انسخ محتواه كاملًا، أو حوّله base64: `base64 -i key.json | tr -d '\n'`.

**3) Vercel**
1. [vercel.com/new](https://vercel.com/new) ← استورد المستودع `wafda`.
2. **Settings ← Environment Variables**:

| المتغير | القيمة |
|---|---|
| `FIREBASE_SERVICE_ACCOUNT` | محتوى ملف JSON (أو base64) |
| `DEMO_MODE` | `true` للتجربة (يعبّئ البيانات التجريبية ويفعّل الصفحتين التجريبيتين) · `false` للإنتاج الحقيقي |
| `PAYMENT_WEBHOOK_SECRET` | سلسلة عشوائية طويلة |
| `CRON_SECRET` | سلسلة عشوائية طويلة |
| `ADMIN_EMAIL` | (الإنتاج) بريد حساب الأدمن — يصله رابط إنشاء كلمة المرور |
| `SMTP_HOST` `SMTP_PORT` `SMTP_USER` `SMTP_PASS` | (الإنتاج) البريد الفعلي. مع Gmail: `smtp.gmail.com` و`465` وبريدك و**كلمة مرور تطبيق** (تتطلب التحقق بخطوتين) |
| `EMAIL_FROM` | اختياري: اسم المرسل، الافتراضي `"وفدة" <SMTP_USER>` |
| `APP_URL` | اختياري (يُستنتج من `VERCEL_PROJECT_PRODUCTION_URL`) |

3. **Deployments ← Redeploy**. أمر البناء `npm run build` يتحقق من Firebase أولًا ويطبع رسالة عربية واضحة إن لم يُضبط، ثم:
   - مع `DEMO_MODE=true`: يعبّئ البيانات التجريبية مرة واحدة.
   - مع `DEMO_MODE=false`: يشغّل [`scripts/bootstrap.ts`](scripts/bootstrap.ts) — يحذف البيانات التجريبية مرة واحدة **فقط إن كانت كل الحسابات تجريبية** (`@wafda.test`)، ويتأكد من القوالب، وينشئ حساب الأدمن من `ADMIN_EMAIL` ويرسل له رابط إنشاء كلمة المرور بالبريد. آمن للتكرار مع كل نشر.
4. [`vercel.json`](vercel.json): `"regions": ["fra1"]` بجانب القاعدة، و`/api/cron` يوميًا (حد الخطة المجانية).

## حسابات التجربة

> للتشغيل المحلي والوضع التجريبي فقط. في الإنتاج (`DEMO_MODE=false`) تُحذف هذه الحسابات تلقائيًا ولا يوجد إلا حساب الأدمن من `ADMIN_EMAIL`.

كلمة المرور لكل الحسابات: **`Wafda@2026`**

| الحساب | البريد | الغرض |
|---|---|---|
| منظّم | `organizer@wafda.test` | 4 فعاليات ورصيد 100 ر.س |
| فريق استقبال | `staff@wafda.test` | معيّن على فعاليتين |
| أدمن | `admin@wafda.test` | لوحة الأدمن `/admin` |
| منظّم آخر | `other@wafda.test` | اختبار عزل البيانات |
| استقبال فعالية أخرى | `staff2@wafda.test` | اختبار تقييد الصلاحيات |

الفعاليات: (1) «ملتقى النادي السنوي» دعوات خاصة مدفوعة بسياسة انتظار، فيها دعوة فردية لم ترد، ودعوة بمرافق لم ترد، ومؤكدة منفردة، ومؤكد مع مرافق حضر ضيفه ولم يحضر مرافقه، ومعتذرة، ورقم يفشل إرساله، ومدعوة بالبريد فقط، ومدعوان لم تُرسل دعوتهما. (2) «ورشة تصميم واجهات المستخدم» رابط عام بقائمة انتظار وأحد المسجلين حضر. (3) «جلسة حوارية» رابط عام مكتمل بسياسة إغلاق. (4) «حفل تخرج الدفعة» مسودة. (5) «اجتماع الشركاء الربعي» لمنظّم آخر. ومعها طلب تصميم بانتظار المراجعة، وطلب وصله عرض سعر، وشكوى مفتوحة. سكربت التعبئة يطبع روابط التجربة الجاهزة.

## رحلة تجربة في 10 دقائق

1. ادخل بـ `organizer@wafda.test` ← «+ فعالية جديدة» ← البيانات ← «خاصة بالاسم».
2. **القالب والمعاينة**: اختر قالبًا وراجع صفحة الدعوة ونص واتساب والبريد ورسالة التأكيد (كلها من دالة عرض واحدة).
3. **المدعوون**: مدعو برقمك المحلي مع «يسمح بمرافق»، وآخر ببريد. أو نزّل الملف النموذجي واستورده (مقبول/مكرر/يحتاج تصحيحًا، تعديل واستبعاد وإعادة تحقق).
4. **الدفع**: الملخص (مثال: 40 دعوة منها 10 بمرافق = 50 مكانًا) ← «ادفع» ← «ادفع الآن (تجريبي)»، ثم «إعادة إرسال نفس الإشعار»: لا يتكرر الأثر.
5. **الإرسال**: التكلفة المتوقعة لكل قناة ← «إرسال الدعوات» ← النتيجة والرصيد.
6. **الضيف** (من الجوال): `/dev/inbox` ← رابط الدعوة ← «معي مرافق» ← «أكّد حضورك» ← تذكرتان مستقلتان، وتذكرة المرافق بزر مشاركة.
7. **الاستقبال**: `staff@wafda.test` أو المنظّم ← «التحضير» ← «تشغيل الكاميرا» ← امسح: «تم تسجيل الدخول»، وأعد المسح: «حضر مسبقًا» بالوقت والطريقة.
8. **تعذّر عرض الرمز**: ابحث بالاسم أو جزء من الجوال ← «تسجيل الحضور يدويًا» للمرافق.
9. **اللوحة**: الدعوات (والأشخاص)، لم يؤكد، المؤكدون (أشخاص + دعوات)، الحاضرون (ضيوف + مرافقون)، المتاح، تعذّر الإرسال، الانتظار، اعتذر، شريط الامتلاء، آخر من حضر ← «تنزيل كشف الحضور CSV».
10. **الصلاحيات والأدمن**: `staff2@wafda.test` يفتح تحضير الفعالية = «غير موجودة». `admin@wafda.test` ← المؤشرات، الحسابات، القوالب، التصاميم، الدعم، الأسعار والسياسات، المدفوعات والإشعارات، الرسائل والتكلفة، سجل التدقيق.

## محاكاة الحالات

| الحالة | كيف |
|---|---|
| فشل نهائي للرسالة (واسترجاع قيمتها) | رقم ينتهي بـ `0000` أو بريد يحتوي `fail` |
| فشل مؤقت ثم نجاح | رقم ينتهي بـ `1111` أو بريد يحتوي `flaky` |
| فشل الدفع / إشعار مكرر | أزرار صفحة `/dev/checkout/[id]` |
| رصيد غير كافٍ | أرسل لعدد يتجاوز الرصيد؛ وبدّل السياسة من `/admin/settings` |

`/dev/inbox`: رسائل واتساب والبريد بروابط قابلة للنقر مع تصفية بالمستلم.

## القرارات المهمة

- **السعة الفعلية = الأقل بين الحد الأقصى والأماكن المدفوعة**، ووثيقة الفعالية (`reserved`) هي الحقيقة الوحيدة للمقاعد. كل حجز في `runTransaction` يقرأ الفعالية والتسجيل والتذاكر والدعوة (وقيد الوسيلة) ثم يكتب — كل القراءات قبل الكتابات.
- **مسار حجز موحّد** (`book` في `rsvp.ts`) تمر منه الدعوة الخاصة والرابط العام وصفحة الإدارة وفرص الانتظار، فلا تختلف القواعد بين المسارات.
- **قيود فريدة بمعرّفات ثابتة**: `inv_<invitationId>`، `<registrationId>_<kind>`، `<eventId>_<userId>`، قيد الرصيد = بصمة مفتاح منع التكرار، التسجيل العام = بصمة (الفعالية + مفتاح النموذج)، ووسيلة التواصل داخل الفعالية في `uniques`.
- **استعلامات بفلاتر مساواة فقط** والترتيب في الذاكرة؛ مؤشرات الأدمن **بعمليات تجميع** (`count`/`sum`) بدل قراءة المجموعات.
- **`regStatus` على الدعوة** يُحدَّث في نفس المعاملة.
- **الأماكن المدفوعة منفصلة عن المحجوز**: الدعوة بمرافق = مكانان في الباقة، ومقعد المرافق يُحجز فقط إن أضافه الضيف.
- **دفعة الرسائل**: الخصم والعناصر في معاملة واحدة، ثم رسائل `<batch>_<i>`، والعامل يكمل المعلّق. **الرسالة** تُحجز بمهلة، 3 محاولات بمهلة متضاعفة، ثم «فشلت» مع قيد استرجاع ثابت المعرّف.
- **الدفع يُثبَّت فقط بالإشعار الموقّع** (توقيع + مبلغ + عملة)؛ كل إشعار يُسجَّل بمعرّفه ويُطبّق أثره مرة واحدة.
- **QR = رابط التذكرة فقط** (160 بت بلا بيانات شخصية). المسح والتحضير اليدوي مسار واحد في معاملة. تذكرة فعالية أخرى = «لا تخص هذه الفعالية» بلا بيانات.
- **الأمان**: عزل المنظّمين (فعالية غيرك = 404) في الصفحات والإجراءات وAPI؛ scrypt؛ جلسة برمز عشوائي تُخزَّن بصمته في كوكي HttpOnly + SameSite=Lax؛ فحص Origin وSec-Fetch-Site فوق حماية Next؛ حد للمحاولات على الدخول والتسجيل والتسجيل العام والتأكيد؛ الإيقاف ينهي الجلسات؛ سجل تدقيق.
- **تحسينات إعادة البناء**: إشعارات عائمة على مستوى الموقع (لا تضيع رسالة النجاح إذا اختفى النموذج بعد إعادة العرض)، فصل كامل بين أدوات الخادم والمتصفح (`shared/` مقابل `server/`)، مؤشرات الأدمن بالتجميع، ومسار حجز واحد بدل عدة مسارات.

**حدود معروفة**: وثيقة الفعالية «ساخنة» (كل حجز يكتب عدّادها)؛ Firestore يتحمّل نحو كتابة/ثانية بثبات على الوثيقة مع دفعات أعلى، والمعاملة تعيد حتى 40 مرة — يكفي لفعاليات بمئات أو آلاف التسجيلات الموزّعة؛ للموجات اللحظية الضخمة يلزم عدّاد مقسّم أو طابور. عامل المهام داخل Next لا يعمل على Vercel (هناك `/api/cron`).

## حالة كل ربط

| الخدمة | الحالة |
|---|---|
| قاعدة البيانات (Firestore) | **فعلي** (حساب خدمة) أو المحاكي محليًا |
| واتساب | التجريبي: صندوق الرسائل · الإنتاج: **غير مفعّل** حتى يُربط مزوّد — يختفي من الواجهات تلقائيًا، والضيوف يؤكدون بالبريد (`MessageProvider` في `src/server/providers/messaging.ts`) |
| البريد | التجريبي: صندوق الرسائل · الإنتاج: **فعلي عبر SMTP** (Gmail بكلمة مرور تطبيق الآن، أو أي مزوّد لاحقًا بنفس المتغيرات) |
| الدفع | التجريبي: صفحة دفع تجريبية بإشعار موقّع · الإنتاج: **تحويل بنكي يدوي** — المنظّم يطلب، والطلب يظهر في `/admin/payments` مع زر التواصل على واتساب، والأدمن يضغط «تأكيد الاستلام» بعد وصول المبلغ فيمر بنفس مسار تثبيت الدفع (مرة واحدة مهما تكرر). بوابة الدفع لاحقًا = تطبيق `PaymentProvider` في `src/server/providers/payments.ts` |
| المهام المجدولة | **فعلي** — instrumentation أو `npm run worker` أو Vercel Cron |

تظهر الحالة أيضًا في `/admin`.

## الاختبارات

**آلية على محاكي Firestore** (`npm test`): **72 اختبارًا ناجحًا** في 10 ملفات:
- 20 تسجيلًا متزامنًا على 5 مقاعد = 5؛ 56 متزامنًا على 50 مكانًا مدفوعًا (والحد الأقصى 90) = 50؛ سياسة الانتظار والإغلاق.
- تأكيدات متزامنة لنفس الدعوة لا تكرر الحجز ولا التذاكر ولا رسالة التأكيد؛ مدعوون مختلفون مع مرافقين لا يتجاوزون السعة.
- مقعد واحد متبقٍ وطلب مرافق (منفردًا، والانتظار بمقعدين).
- مفتاح النموذج المكرر = نفس التسجيل؛ نفس الرقم بصيغة مختلفة لا يكرر ولا يكشف التذكرة ويعيد الإرسال لصاحبه مرة ضمن المدة.
- الاعتذار يحرر المقاعد وتكراره آمن؛ الباقة 40+10=50؛ التسجيل مغلق قبل الدفع.
- رمزا المدعو والمرافق مستقلان (160 بت)؛ المسح المكرر والتحضير اليدوي والمسح المتزامن لا تكرر الحضور.
- عضو غير معيّن ممنوع؛ رابط إنشاء كلمة المرور لمرة واحدة؛ تذكرة فعالية أخرى لا تكشف بياناتها؛ البحث مقيّد بالفعالية وبأي صيغة.
- الانتظار: منع الفرصة بلا مقعد أو رصيد، خصم مرة واحدة، أخذ المقعد قبل التأكيد، انتهاء الفرصة.
- الدفع: تكرار الإشعار متتابعًا ومتزامنًا، رفض التوقيع والمبلغ والعملة، الشحن مرة واحدة، الأماكن الإضافية، شروط الدفع.
- الرسائل: الخصم حسب القناة، الضغط المتكرر، الرصيد غير الكافي بالسياستين، الفشل والاسترجاع، 3 محاولات، التذكير لمن لم يرد فقط، التذكير المجدول يفحص الحالة ولا يُنفّذ مرتين، والفشل بسبب الرصيد بلا إرسال جزئي، ومنع الإرسال عند تجاوز الباقة.
- الاستيراد: تصنيف الصفوف، Excel بعناوين عربية/إنجليزية وأرقام بلا صفر، CSV، رفض ‎.xls؛ توحيد الأرقام السعودية بكل الصيغ والأرقام العربية.
- عزل المنظّمين في 22 عملية؛ التصاميم والدعم؛ قراءة QR بـ jsQR.
- الإنتاج: تأكيد الدفع اليدوي متزامنًا ومتكررًا = تفعيل واحد، الإلغاء ثم التأكيد، رقم التواصل؛ واتساب غير مفعّل لا يُرسل عليه ولا تُحسب تكلفته والضيف يؤكد بالبريد؛ نص البريد مهرّب.

**الرحلة كاملة في متصفح حقيقي** (`npm run test:e2e`، Playwright على بناء إنتاجي، جوال وكمبيوتر): **8 مراحل ناجحة** — إنشاء ← قالب ← مدعوون ← دفع ← إرسال ← فتح الدعوة من الصندوق على الجوال وتأكيد مع مرافق ومنفرد ← **مسح QR بكاميرا افتراضية** (Chromium بـ `--use-file-for-fake-video-capture` على y4m مولّد بـ ffmpeg من تذكرة حقيقية) بـ BarcodeDetector ثم jsQR ← «حضر مسبقًا» ← المرافق يدويًا وإدخال الرابط ← منع غير المعيّن (واجهة + API) ← اللوحة وCSV ← العام والمكتمل ← العزل ← زيارة 75 صفحة بلا أخطاء وبلا تمرير أفقي على الجوال. اللقطات في `e2e/.artifacts/` وقد رُوجعت يدويًا.

## الافتراضات

- نوع الدعوة لكل فعالية واحد، ولا يتغير بعد الدفع.
- الضيف بلا حساب ولا رمز تحقق في النسخة الأولى.
- رسالة التأكيد تحمل رابط صفحة التذكرة (QR في الصفحة)؛ إرفاق الصورة مع اختيار المزوّد.
- رسالة فرصة الانتظار من رصيد الرسائل.
- العرض بتوقيت الرياض وتقويم ميلادي وأرقام لاتينية.
- **إعادة إرسال التذكرة** (من المنظّم أو عند إدخال وسيلة مسجلة في الرابط العام) تُعامل كرسالة تأكيد: مشمولة في الباقة بتكلفة تشغيل تقديرية، وبحد أدنى بين كل إعادة (10 دقائق افتراضيًا).
- **دعوة عضو الاستقبال** على حساب المنصة.
- **الرابط العام بلا مرافقين** (مقعد لكل تسجيل).
- السعة في الدعوات الخاصة أيضًا = الأقل بين الحد الأقصى والمدفوع، فيمكن دعوة أكثر من الحد مع سياسة انتظار.
- من **ألغى المنظّم** تسجيله لا يعيد التأكيد من رابطه (بخلاف المعتذر).
- لا اعتذار ولا إلغاء بعد تحضير أي تذكرة من التسجيل.
- يمكن إرسال أكثر من فرصة لمقعد واحد، ويفوز من يؤكد أولًا.
- لم تُطلق `cacheComponents` في Next 16 (كل الصفحات ديناميكية لأنها تقرأ بيانات حية).
- اسم المستودع لاتيني لأن GitHub لا يقبل الأحرف العربية.
- الأسعار تجريبية مُعلّمة (باقات 50/100/250/500/1000 بـ 99/179/399/699/1199 ر.س، المكان الإضافي 2 ر.س، واتساب 0.25، بريد 0.05) وقابلة للتعديل من `/admin/settings`.
- لم تُرفق ملفات الهوية الرسمية؛ الشعار والقوالب مبنية من الألوان المحددة.

## القرارات المفتوحة

1. **مزوّد واتساب** (WhatsApp Business Platform) واعتماد القوالب — النصوص جاهزة كقوالب بمتغيرات في `texts.ts`. حتى ذلك الحين القناة مخفية.
2. **دومين خاص للبريد**: Gmail يكفي للبداية (حد يومي ~500 رسالة)، ومع دومين خاص ومزوّد بريد تتحسن الثقة وحد الإرسال — يكفي تغيير متغيرات SMTP.
3. **بوابة الدفع** المحلية (Moyasar/Tap…) بدل التحويل اليدوي — يكفي تطبيق `PaymentProvider` (رابط الدفع + التحقق من توقيع الإشعار).
4. **الأسعار النهائية**: الباقات، المكان الإضافي، سعر الرسالة لكل قناة، تكلفة رسائل التأكيد.
5. **مكان البيانات (PDPL)**: إن لزم بقاؤها في المملكة: Firestore في الدمام `me-central2` **واستضافة داخل المملكة بدل Vercel**. موقع Firestore لا يتغير بعد الإنشاء، فيُحسم قبل إنشاء قاعدة الإنتاج.
6. **خطة Vercel**: المجانية تشغّل المهام المجدولة مرة يوميًا؛ لدقة بالدقيقة Pro أو cron خارجي يستدعي `/api/cron` بـ `Authorization: Bearer CRON_SECRET`.
7. **ملفات الهوية الرسمية** (Brand Guide وBrand Kit).
8. **الإطلاق الأول**: تجربة على ورشة أو فعالية حقيقية واحدة لقياس وقت التجهيز، وسرعة الدخول، ودقة الكشف، واستعداد الدفع، وتكلفة رسائل التأكيد قبل اعتماد الأسعار.
